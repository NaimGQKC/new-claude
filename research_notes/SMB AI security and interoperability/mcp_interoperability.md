# MCP interoperability: exposing an AI workspace (LibreChat-based) as a remote MCP server, and how Claude, ChatGPT, Gemini, Copilot connect (as of 2026-11-20)

Method note: research was done with WebSearch/WebFetch on 2026-11-20. OpenAI's help-center page (help.openai.com) returned HTTP 403 to fetch, so ChatGPT plan/admin facts rest on search-result summaries of OpenAI help pages plus the fetched OpenAI developer docs. GitHub repo metadata (stars/licenses/activity) could not be retrieved (the sandbox had no GitHub access), so open-source server maturity is unverified. Cursor / Claude Code connection details were not researched in this pass (see Gaps).

## 1. Which platforms/plans allow custom remote MCP connectors, who must approve, and what do they require?

### Takeaway
All four ecosystems now accept custom remote MCP servers over HTTPS with Streamable HTTP and OAuth, but they differ sharply on who can add them. On Claude Team and ChatGPT Business, only admins/owners can add them. Claude Pro/Max users can add their own. Gemini Enterprise and Microsoft 365 Copilot are admin/developer-gated, with their own fixed redirect URIs. A single OAuth 2.1 server with Protected Resource Metadata, PKCE, a CIMD-capable authorization server and a DCR fallback covers all of them.

### Cited Findings

**Claude (claude.ai, Desktop, Cowork)**
- Custom connectors via remote MCP are available on Free, Pro, Max, Ultra, Team and Enterprise; Free is limited to one custom connector. — [Anthropic support: Get started with custom connectors using remote MCP](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)
- Who adds: on Team only Owners/Primary Owners; on Enterprise Owners, Primary Owners and custom roles with "Manage access to Libraries"; on Pro/Max the individual adds it under Customize > Connectors. After the org adds one, members connect individually. — [Anthropic support](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)
- Auth options in the UI: "Sign in now", "Sign in when needed", "No sign in". OAuth client choices: Claude's published identity (recommended), automatic registration (DCR) or your own client ID/secret. Fixed credentials (API key/bearer) can be sent as request headers, stored encrypted. — [Anthropic support](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)
- Redirect URL to allow-list: `https://claude.ai/api/mcp/auth_callback`. — [Anthropic support](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)
- Network: connections originate from Anthropic's cloud (not the user's device); the server must be reachable on the public internet on port 443 only; private/VPN servers need Anthropic's IP ranges allow-listed (ranges published at platform.claude.com/docs/en/api/ip-addresses). — [Anthropic support](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)
- No general tool-count limit is stated; users can disable individual tools in "Search and tools"; owners can disable specific tool calls that render interactive connectors. — [Anthropic support](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)
- A search-result summary of Anthropic's help pages states that on Team/Enterprise "everyone who uses the connector reaches the service with the same credential" and that editing a connector requires removing and re-adding it; this was NOT in the fetched version of the page and conflicts in emphasis with "members connect individually", so treat as unverified. — [Anthropic support (search summary)](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp.md)
- Transport (Streamable HTTP vs SSE) and CIMD are not named on the fetched Anthropic connector page; the page does not state beta status. — [Anthropic support](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)
- Anthropic says MCP 2026-07-28 support "is being rolled out across Claude products" (no product list or dates). The post also mentions enterprise-managed auth (admins provision connectors org-wide via their identity provider) and MCP Apps (inline interactive UI), and says the stateless core lets servers run on serverless/edge. — [Claude blog: Bringing MCP 2026-07-28 to Claude](https://claude.com/blog/bringing-mcp-2026-07-28-to-claude)

**ChatGPT (OpenAI)**
- Business: only admins/owners can enable developer mode and create/publish custom MCP apps; admins cannot enable it for individual members; each admin must enable it for themselves. Enterprise/Edu: admins can delegate developer-mode access to specific members via RBAC; only admins/owners can publish. — [OpenAI help center: Developer mode and MCP apps (as summarized by search)](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt)
- OpenAI states it is the builder's responsibility to vet custom apps/connectors; untrusted MCP servers risk prompt injection. — [OpenAI help center (search summary)](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-connectors)
- Business/Enterprise admins can refresh a custom MCP app's tool list from workspace app settings; an older version said tools/metadata required recreating and republishing. Sources show differing versions of the same help article (the article was renamed several times: "connectors" -> "apps" -> "custom apps/plugins"). — [OpenAI help center (search summary)](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-connectors)
- Plus/Pro: a third-party Boomi guide says individual Plus/Pro users can connect custom MCP servers with Developer Mode (Settings > Apps & Connectors > Advanced), described as read/fetch-focused; a late-2025 launch article called full MCP access "beta" for Plus/Pro. A community post suggests the explicit developer-mode toggle was later removed for eligible users, but this is unconfirmed. — [Boomi guide](https://help.boomi.com/docs/Atomsphere/Platform/Connect_chatgpt_setup); [InfoQ](https://www.infoq.com/news/2025/10/chat-gpt-mcp); [OpenAI community thread](https://community.openai.com/t/mcp-server-tools-now-in-chatgpt-developer-mode/1357233.md?page=2)
- Current "Connect from ChatGPT" doc: in ChatGPT Plugins press plus > "Add custom MCP server", give name/description, choose connection method, configure auth, accept the risk warning, "Create as a plugin". Public endpoints must be HTTPS with Streamable HTTP (typically `/mcp`); SSE is not mentioned. Account/workspace policies apply; public plugin submission needs a stable public HTTPS endpoint; published plugins get tool updates via continuous review. — [OpenAI Apps SDK: Connect from ChatGPT](https://developers.openai.com/apps-sdk/deploy/connect-chatgpt)
- Private servers: "Secure MCP Tunnel" (outbound tunnel, no inbound ports); tunnels do not support public plugin submission. A community thread reports tunnel association failing for a Business workspace/Platform org pair (user report). — [OpenAI Secure MCP Tunnel guide](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels); [OpenAI community](https://community.openai.com/t/secure-mcp-tunnel-workspace-org-association-fails-and-support-says-there-is-no-manual-fix/1384494)
- OAuth requirements (Apps SDK auth doc): serve Protected Resource Metadata (`resource`, `authorization_servers`); AS metadata must include `S256` in `code_challenge_methods_supported`; CIMD is preferred (ChatGPT uses an HTTPS URL as client_id; supports `none`+PKCE and `private_key_jwt`); DCR still supported (one client per connection); ChatGPT sends the `resource` parameter on auth and token requests and the server must validate signature, issuer, audience, expiry and scopes on every request. — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)
- Redirect URIs: `https://chatgpt.com/connector/oauth/{callback_id}` (servers without RFC 9207 support) or the stable `https://chatgpt.com/connector_platform_oauth_redirect` (servers that advertise `authorization_response_iss_parameter_supported: true` and return an exact-match `iss`); copy the exact URI shown on the server management page. — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)
- ChatGPT does NOT support client-credentials, service accounts, JWT-bearer assertions, custom API keys or customer mTLS; it presents an OpenAI-managed client cert (SAN `mtls.prod.connectors.openai.com`) you can validate, and publishes egress IP ranges you can allow-list. Workspace domain restrictions need `openid`+`email` scopes and a UserInfo endpoint returning `email_verified: true`. Per-tool `securitySchemes` (`noauth`/`oauth2`) trigger the link UI; an optional `_meta["openai/profile"]` profile tool helps multi-account. — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)
- Note: ChatGPT is adopting the CIMD transition in MCP SEP-3149 (plural `token_endpoint_auth_methods_supported` plus legacy singular field during transition). — [OpenAI Apps SDK: Authentication](https://developers.openai.com/apps-sdk/build/auth)

- Limits: at most 100 actions (tools) enabled at a time; all actions off by default and enabled by admin; calls require user confirmation unless the tool has `readOnlyHint`; data store must be created inside an app. Private servers go through Agent Gateway (us-central1, europe-west1). Preview/GA status not stated on the page. — [Google Cloud docs](https://docs.cloud.google.com/gemini/enterprise/docs/connectors/custom-mcp-server/set-up-custom-mcp-server)

**Microsoft 365 Copilot / Copilot Studio**
- Declarative agents in M365 Copilot can wrap a remote MCP server as a plugin; auth types are OAuth (static registration), OAuth (dynamic registration/DCR), Entra SSO, or none; redirect URI to register: `https://teams.microsoft.com/api/platform/v1.0/oAuthRedirect`; tools can be discovered dynamically (including MCP-app widgets) or pinned; the user needs custom-app upload and Copilot access enabled by the tenant admin. - Agent 365 "bring your own MCP server" governance is in preview (some surfaces unsupported). ### Inferences
- A single server should: be public HTTPS on 443 at a stable `/mcp`; use Streamable HTTP only; publish RFC 9728 PRM and RFC 8414/OIDC AS metadata with S256 PKCE; validate `aud`/`resource`; support CIMD plus a DCR fallback plus a pre-registered-client path (Gemini and Copilot-static need pre-registered client ID/secret); allow-list the redirect URIs above (claude.ai, chatgpt.com x2, vertexaisearch, teams.microsoft.com).
- "Power users add it themselves" is true for Claude Pro/Max and (reportedly) ChatGPT Plus/Pro, but a Claude Team or ChatGPT Business user cannot: an owner/admin must add it, and on ChatGPT Business the admin cannot delegate developer mode. Gemini Enterprise needs a Google Cloud org admin to lift an org-policy block. This is the main rollout friction for an SMB.
- ChatGPT's no-API-key/no-client-credentials rule means a "shared service account" design cannot be wired to ChatGPT except via per-user OAuth.
- I found no per-seat fee for custom connectors on the pages reviewed; cost is the plan itself (Copilot requires a Microsoft 365 Copilot license; Gemini Enterprise is a paid Google product).

## 2. Current MCP spec version, deprecations and what they mean for a server we build

### Takeaway
The current spec is 2026-07-28 (released July 28, 2026; previous revision 2025-11-25). It makes the Streamable HTTP transport stateless (no sessions, no initialize handshake), deprecates DCR in favor of Client ID Metadata Documents, and deprecates HTTP+SSE, Roots, Sampling and Logging. Authorization stays OAuth 2.1 with mandatory Protected Resource Metadata and audience-bound tokens. Clients are still rolling out support, so a server should serve both the stateless and older revisions during migration.

### Cited Findings
- 2026-07-28 changes vs 2025-11-25: protocol-level sessions and `Mcp-Session-Id` removed; `initialize` handshake removed (each request carries protocol version and client capabilities in `_meta`); new mandatory `server/discover` RPC; `subscriptions/listen` replaces the GET stream and resource subscribe; `ping` and `logging/setLevel` removed; tasks moved to an official extension; Multi Round-Trip Requests replace server-initiated sampling/elicitation/roots requests; all results carry `resultType`; SSE resumability (`Last-Event-ID`) removed. — [MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Minor: required `Mcp-Method`/`Mcp-Name` headers on POSTs; `ttlMs` and `cacheScope` required on list/read results; servers SHOULD return `tools/list` in deterministic order (helps client caching and LLM prompt-cache hits); `inputSchema` allows any JSON Schema 2020-12 keywords; resource-not-found now `-32602`; error code allocation (`-32020`..`-32099` reserved). — [MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Deprecations (12-month minimum window under the new lifecycle policy): Roots, Sampling, Logging; HTTP+SSE transport (deprecated since 2025-03-26, now formally Deprecated); `includeContext` "thisServer"/"allServers"; OAuth Dynamic Client Registration (RFC 7591) "in favor of Client ID Metadata Documents", retained for backward compatibility. — [MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Authorization (2026-07-28): authorization servers MUST implement OAuth 2.1; AS and clients SHOULD support CIMD; DCR is MAY and deprecated; MCP servers MUST implement RFC 9728 Protected Resource Metadata; AS MUST offer RFC 8414 or OIDC discovery; clients MUST send RFC 8707 `resource` on auth and token requests; servers MUST validate tokens were issued for them (audience) and MUST NOT accept or pass through other tokens; tokens only in the `Authorization` header, never the query string; 401 for invalid/expired, 403 for insufficient scope with `WWW-Authenticate` `error="insufficient_scope"` and scope guidance; AS SHOULD return RFC 9207 `iss` (clients MUST validate if present); clients must key credentials by issuer and re-register if the AS changes; clients must specify `application_type` in DCR. — [MCP authorization spec 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization); [changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Authorization is optional in the spec; STDIO servers should not use it. — [MCP authorization spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Release timing is inconsistent across secondary sources (RC published May 21 vs June 29 per listings); the changelog itself is authoritative. Third-party write-ups exist (WorkOS, Composio, AAIF migration guide) but were not read in full. — [search results](https://blog.modelcontextprotocol.io/posts/2026-07-28/); [AAIF migration post](https://aaif.io/blog/mcp-2026-07-28-whats-changing-and-how-to-migrate)
- ChatGPT's docs reference both 2025-11-25 and 2026-07-28 authorization behavior. — [OpenAI Apps SDK auth](https://developers.openai.com/apps-sdk/build/auth)
- Gemini Enterprise documents Streamable HTTP only, consistent with SSE deprecation. — [Google Cloud docs](https://docs.cloud.google.com/gemini/enterprise/docs/connectors/custom-mcp-server/set-up-custom-mcp-server)

### Inferences
- Build on an SDK that supports both 2025-11-25 (with sessions/initialize) and 2026-07-28 (stateless) negotiation; stateless design (explicit server-minted handles instead of sessions) is also the easiest to host behind a load balancer next to LibreChat.
- Avoid Roots/Sampling/Logging and SSE; do not make DCR the only registration path; CIMD requires the authorization server (not just the MCP server) to fetch/validate client metadata, which matters when choosing an IdP.
- Because client support for 2026-07-28 is still rolling out (Anthropic) the safe default for Nov 2026 is dual-version support.

### Gaps
- Exact per-client (Claude, ChatGPT, Gemini, Copilot, Cursor) support status for 2026-07-28 stateless transport not found.
- The 2025-11-25 revision's own changelog (e.g., CIMD introduction, URL elicitation, tasks) was not fetched; only inferred from references in the 2026-07-28 changelog.

## 3. LibreChat as MCP client / server, and candidate open-source servers as a neutral shared layer

### Takeaway
LibreChat's documentation describes it only as an MCP client (Streamable HTTP, SSE, stdio, OAuth with DCR, per-user API keys, Entra OBO, agent tool library). I found no documentation or issue showing it acting as an MCP server for agents, files or memory, so a "company brain" would be a separate MCP server that LibreChat itself connects to as a client. Candidate OSS memory servers exist but their maturity could not be verified.

### Cited Findings
- LibreChat remote MCP servers use Streamable HTTPS or SSE (chosen when a user creates one in the UI); stdio servers only via admin `librechat.yaml`; UI-created servers can reach remote URLs only. — [LibreChat MCP docs](https://www.librechat.ai/docs/features/mcp)
- Auth: None (auto-detect OAuth), API key (shared or per-user; Bearer/Basic/custom), OAuth (client ID/secret or DCR when empty), and On-Behalf-Of (admin-granted; requires OpenID Connect login, Entra ID given as example). Connections/tokens/credentials are per user; refresh tokens renewed in background; OAuth sign-in has a 10-minute timeout. — [LibreChat MCP docs](https://www.librechat.ai/docs/features/mcp)
- Agents: builders add MCP servers via the Tool Library and choose which tools to keep; per-tool options Defer loading, Programmatic, Background, Intent label; admins can attach server instructions added to model context; servers can add/remove tools at runtime; MCP Apps render in sandboxed frames; UI-created servers can be shared with users/groups/roles/everyone. — [LibreChat MCP docs](https://www.librechat.ai/docs/features/mcp)
- OAuth callback pattern `${DOMAIN_SERVER}/api/mcp/<server-name>/oauth/callback` must be registered with the provider; `requiresOAuth` auto-detected if unset. A GitHub issue (#13401) reports an OAuth bearer-token/audience (`resource`) problem. — [LibreChat mcp_servers reference](https://www.librechat.ai/docs/configuration/librechat_yaml/object_structure/mcp_servers); [issue #13401](https://github.com/danny-avila/LibreChat/issues/13401) (from search snippet, not opened)
- The MCP docs page does not mention LibreChat acting as an MCP server; my search for a feature request to expose agents as an MCP server found none. — [LibreChat MCP docs](https://www.librechat.ai/docs/features/mcp)
- Candidate OSS "memory/knowledge" servers: mcp-memory-service (PyPI; described as REST+MCP+OAuth 2.1, multi-user, knowledge graph; one listing noted refresh tokens not yet supported) — [PyPI](https://pypi.org/project/mcp-memory-service/); Memlord (self-hosted MCP memory server for teams; per-user private memories plus shared workspaces; in-process OAuth 2.1 authorization server; PostgreSQL+pgvector; AGPL-3.0 with commercial option per the search summary) — [mcpservers.org listing](https://mcpservers.org/servers/myrikld/memlord). Licenses, stars and activity were not verified from the repos.

### Inferences
- Realistic architecture: LibreChat stays an MCP client of our company-brain server (using its OAuth/DCR or OBO with Entra), while Claude/ChatGPT/Gemini/Copilot connect to the same server; LibreChat agents and external tools then see the same data.
- If LibreChat "projects" and "memory" must be exposed, that needs a small adapter service reading LibreChat's MongoDB/API; this was not found as an existing feature (absence of evidence in docs, not proof).
- AGPL (Memlord) is workable for internal network-service use only if modifications are published; evaluate against our licensing stance.

### Gaps
- No verified information on LibreChat's own APIs (agents API / OpenAI-compatible endpoints) as an MCP-adjacent surface; GitHub was inaccessible from this environment.
- Stars/licenses/last commit for LibreChat, modelcontextprotocol/servers (filesystem, memory reference servers), Obsidian/Notion/Drive/SharePoint MCP servers were not retrieved. No evidence gathered on official Notion/Google Drive/SharePoint MCP servers' availability or auth.
- Whether LibreChat honors the 2026-07-28 stateless transport or CIMD as a client was not found.

## 4. Practical designs: own "company brain" MCP server vs. connecting tools to Drive/SharePoint/Notion MCP servers

### Takeaway
Research on this specific design question yielded only indirect evidence. The platform docs show that either design is technically feasible; the deciding factors are who owns permissions and how many admin approvals each platform needs.

### Cited Findings
- Claude offers org-wide provisioning of connectors through enterprise-managed auth via the company IdP (Entra/Okta), which suggests an IdP-centric design reduces per-user setup. — [Claude blog](https://claude.com/blog/bringing-mcp-2026-07-28-to-claude)
- ChatGPT's connector OAuth supports workspace-domain restriction (via `openid`, `email`, `email_verified`), which lets a server restrict sign-in to the company domain. — [OpenAI Apps SDK auth](https://developers.openai.com/apps-sdk/build/auth)
- Microsoft's Copilot path supports Entra SSO for MCP plugins natively. — [Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/build-mcp-plugins)
- Gemini Enterprise needs a pre-registered OAuth client and an admin to lift the org policy; actions are enabled by admin (max 100). — [Google Cloud docs](https://docs.cloud.google.com/gemini/enterprise/docs/connectors/custom-mcp-server/set-up-custom-mcp-server)

### Inferences
- Own server: single place for project instructions, decisions and memory (data that does not live in Drive/SharePoint) and a single audit log; cost is building/hosting an authorization-aware server and one admin approval per platform.
- Vendor MCP servers (Drive/SharePoint/Notion): zero new infrastructure and permissions follow the source system's ACLs, but each tool needs its own connector setup and the data sets do not include LibreChat-native projects/memory.
- A hybrid (own thin server for notes/decisions/memory/project instructions plus vendor MCP servers for documents) minimizes build effort; this is a design judgment not stated in any source.
- Use Entra or Google Workspace as the single IdP so Claude, ChatGPT and LibreChat users map to the same identity and ACLs.

### Gaps
- No sources found comparing the designs or documenting existing deployments; availability/auth of official Notion, Google Drive and SharePoint/Microsoft Graph MCP servers not verified (a Microsoft Learn page on a Microsoft Graph enterprise MCP server for Copilot Studio appeared in search results but was not read).

## 5. Security risks of cross-platform sharing and mitigations

### Takeaway
The main risks are tool poisoning/cross-server shadowing via descriptions, prompt injection via shared documents, over-broad tokens and loss of per-user permissions through shared credentials. Spec-level controls (audience-bound tokens, scope challenges, no token passthrough) plus least-privilege scopes, per-user OAuth, read-only defaults, human confirmation and scanning are the documented mitigations.

### Cited Findings
- Tool poisoning delivers malicious instructions in tool descriptions (metadata), and the LLM sees all tool descriptions from all connected servers, enabling cross-server shadowing; OWASP recommends treating each MCP server as an untrusted, independent security domain and preventing one server's descriptions from referencing others' tools. — [OWASP MCP Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html); [Netskope](https://www.netskope.com/blog/securing-llm-superpowers-when-tools-turn-hostile-in-mcp)
- Mitigations cited: scanning (mcp-scan), quarantine of servers whose metadata reference other tools, prompt-injection classifiers (not sufficient alone), signing/policy controls, runtime monitoring, least-privilege OAuth scopes. OWASP cautions that optional signing should not be presented as a requirement. — [OWASP cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html); [CSA whitepaper, May 2026](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/05/CSA_whitepaper_mcp_security_tool_poisoning_20260506-csa-styled.pdf); [CSA research note, July 2026](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/07/CSA%5Fresearch%5Fnote%5Fmcp%5Ftool%5Fpoisoning%5Fai%5Fagent%5Fexfiltration%5F20260702-csa-styled.pdf)
- An arXiv study of seven MCP clients found strong guardrails in some (e.g., Claude Desktop) and high susceptibility to cross-tool poisoning in others (e.g., Cursor). — [arXiv 2603.21642](https://arxiv.org/html/2603.21642)
- Spec controls: token audience validation (RFC 8707), no token passthrough, tokens only in Authorization header, scope minimization with step-up via `insufficient_scope`, RFC 9207 issuer validation against mix-up, credentials bound to issuer. — [MCP authorization spec 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Platform-side controls: ChatGPT lets you validate OpenAI's client cert (mTLS) or allow-list egress IPs, requires per-tool `securitySchemes`; Gemini requires user confirmation for non-`readOnlyHint` tools and off-by-default actions; Claude lets users/owners disable individual tools; OpenAI warns that untrusted servers increase prompt-injection exposure. — [OpenAI Apps SDK auth](https://developers.openai.com/apps-sdk/build/auth); [Google Cloud docs](https://docs.cloud.google.com/gemini/enterprise/docs/connectors/custom-mcp-server/set-up-custom-mcp-server); [Anthropic support](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)
- ChatGPT business-plan connectors reportedly use a frozen snapshot of server tools until an admin republishes (a third-party claim, which also limits rug-pull changes). — [OpenAI community / third-party summary](https://community.openai.com/t/write-actions-blocked-on-custom-mcp-server-business-plan-workspace-developer-mode-unavailable-at-workspace-level/1384381)

### Inferences
- Shared documents are an injection channel: any content a user can write that another user's AI will read (decisions, notes, project instructions) can carry instructions; treat retrieved content as untrusted data, mark provenance in tool output, and keep write tools separate and confirmed.
- Per-user OAuth with identity-based ACL filtering in the server preserves "same permissions" across Claude/ChatGPT/LibreChat; a shared service account (supported by Claude header auth, not by ChatGPT) collapses everyone to the broadest privilege and breaks audit attribution.
- Log every tool call with user `sub`, client_id, tool, resource IDs; keep our own tool descriptions short, static and versioned (the deterministic ordering requirement also helps cache hits).
- Token cost: each tool definition occupies context on every request in every client; no numeric figures were found, so keep the tool count small (Gemini caps at 100 enabled; none of the others publishes a cap).
