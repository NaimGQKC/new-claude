# Automatic per-task model routing, specialized/distilled models, and document-artifact generation (state as of 2026-11-18)

Method note: figures below come from pages fetched/searched in this session. Several fetches returned summaries by a small model, so exact numbers (stars, prices) should be re-checked on the live page before publication. Vendor marketing claims are flagged "(vendor claim)".

## 1. Routing systems: what exists, how each decides, license, self-hostable, budgets

### Takeaway
The routing landscape has split into (a) open-source gateways you self-host (LiteLLM, Portkey gateway, Plano, vLLM Semantic Router, OpenZiti llm-gateway), (b) hosted routers (OpenRouter Auto, Not Diamond, Martian, Requesty), and (c) research routers (RouteLLM, pareto-router). For a task-typed assistant, the practical pattern in 2026 is a gateway with a cheap heuristic/LLM tier classifier plus explicit rules, not a learned router. Most "learned" routers are unproven against a simple baseline (see section 2).

### Cited Findings
- **RouteLLM (LMSYS)**: Apache-2.0, ~5.7k stars. Each router estimates the probability the strong model beats the weak model, and routes to the strong model if that exceeds a cost threshold calibrated on sample queries (Chatbot Arena data by default). Five routers: `mf` (recommended), `sw_ranking`, `bert`, `causal_llm`, `random`. It is strictly binary (strong vs weak). README claims "up to 85% cost reduction while maintaining 95% GPT-4 performance" on MT Bench (self-reported). I could not confirm the date of the last commit. — [GitHub](https://github.com/lm-sys/RouteLLM); [paper abstract](https://arxiv.org/abs/2406.18665) (abstract itself says "over 2 times" cost reduction in certain cases with no quality loss, and that routers keep working when the model pair is swapped at test time)
- **LiteLLM** (BerriAI): ~63.5k stars; gateway with virtual keys, multi-tenant spend tracking per project/user, retry/fallback Router, load balancing, and "auto routing". The README mentions features under a "LiteLLM Commercial License" (so it is not purely MIT; one third-party roundup calls the core MIT, so treat "MIT core + commercial enterprise features" as the likely reality and verify the enterprise-feature split before relying on e.g. SSO/some budget features). — [GitHub](https://github.com/BerriAI/litellm); [roundup saying MIT](https://www.developersdigest.tech/llm-gateways/not-diamond) (secondary; search summary)
- **LiteLLM Auto Routing (beta, v1.94+)**: "complexity router" classifies each request into SIMPLE / MEDIUM / COMPLEX / REASONING, each tier mapped to a model or a pool. Classifier options: heuristic scorer (default, zero API calls, 7 dimensions e.g. length, code presence, reasoning markers), small-LLM classifier with structured output, keyword rules (optionally embedding matching), or custom plugin. Optional Thompson-sampling within a tier pool (`adaptive`), image/modality routing, and **`session_affinity` (off by default) that pins a session's first-turn model to preserve prompt caches**. Classifier-failure fallbacks and context-window escalation exist. The older semantic router is deprecated (adds ~100-500 ms, no session pinning). — [LiteLLM auto routing docs](https://docs.litellm.ai/docs/proxy/auto_routing)
- **LiteLLM's own benchmark (vendor claim, by the router's author)**: vs an all-flagship baseline, 40.4% cheaper at 97.1% relative quality on six public benchmarks; 74.5% cheaper at 87.3% quality on RouterArena; production 51.1% saving ($11,736 vs $23,985 counterfactual) over 272,876 requests; Terminal-Bench 2.0 21-task subset ~27% cheaper with the same 16/21 solves; blind shadow eval on 143 turns: router won 9.8%, tied 78.3%, lost 11.9% (LLM judge). Authors' own caveats: single run, own traffic, LLM judge, flagship-only counterfactual rather than real alternative spend. — [LiteLLM benchmarks](https://docs.litellm.ai/docs/auto_router/benchmarks)
- **OpenRouter Auto Router**: no extra fee over the selected model's price. A fast "decision model" rates the request on ~11 aspects (task type, difficulty, vision need, etc.), then a policy weighs that against live prices, cache status and benchmark performance within your `cost_tier` (low/medium/high) to pick a model **and reasoning effort**. Supports `allowed_models`/`excluded_models` (hard limits), `provider.max_price`, guardrails/ZDR/BYOK constraints; global data region only. Hosted only (not self-hostable). The page does not say which engine powers it. — [OpenRouter Auto Router docs](https://openrouter.ai/docs/guides/routing/routers/auto-router)
- **Not Diamond**: hosted router; current pricing page lists pay-as-you-go "$0.05 per million tokens routed" (waitlist access) and Enterprise (contact sales, "privacy-preserving deployment"); no self-host/VPC detail on the page. Older pricing/aggregator pages mention per-customer trained custom routers and an enterprise VPC option (secondary, possibly outdated). — [Not Diamond pricing](https://www.notdiamond.ai/pricing); [aggregator summary](https://www.orcarouter.ai/blog/not-diamond-vs-martian)
- **Martian**: hosted router; free dev tier of 2,500 requests and enterprise VPC mentioned only by third-party aggregators; self-hosting not a standard option. Weak evidence (aggregator pages with possibly stale data). — [LLM Reference](https://www.llmreference.com/router/martian); [Orca comparison](https://www.orcarouter.ai/blog/not-diamond-vs-martian)
- **Portkey gateway**: MIT, ~13.4k stars; conditional routing, load balancing, fallbacks (configurable on which errors), 40+/50+ guardrails. Semantic caching is hosted/enterprise only; budgets are documented as a platform (managed) feature, not clearly in the open-source package. README says enterprise gateway is merging into open source in a 2.0 pre-release. One docs page says Portkey is now "PRISMA AIRS AI Gateway" (naming in flux). — [GitHub](https://github.com/Portkey-AI/gateway); [Portkey docs](https://portkey.ai/docs/product/ai-gateway)
- **Requesty**: hosted gateway; "smart routing" classifies request by task type (~50 ms per its blog) via a `smart-task` alias; PeakEWMA health-based provider selection, fallback chains, per-user/team budgets and cost tracking. All figures are vendor marketing ("up to 80%" savings unverified). — [Requesty smart routing blog](https://www.requesty.ai/blog/smarter-than-human-model-picking-introducing-requesty-smart-routing); [Requesty on gateways](https://requesty.ai/blog/how-llm-gateways-slash-ai-spend-by-up-to-80-1751653851)
- **vLLM Semantic Router**: Apache-2.0, ~6.5k stars; Envoy ExtProc-based "decision layer" (OpenAI-API compatible) routing across vLLM/OpenAI/Anthropic/Azure/Bedrock/Gemini/Vertex backends; signal-driven (embeddings, keywords, classifiers) with a typed DSL, 13 selection algorithms per its paper (incl. cascade), PII/jailbreak/hallucination plugins, similarity caching, Prometheus/Grafana. Latest named release in repo news: v0.4 "Hermes" (2026-09-24). No cost-tracking/budget feature described on the repo page. Naming inconsistent (paper says Mixture-of-Modality, README Mixture-of-Models). — [GitHub](https://github.com/vllm-project/semantic-router); [paper](https://arxiv.org/abs/2603.04444v4)
- **Plano (formerly Arch) by Katanemo**: Apache-2.0, ~7.1k stars; AI-native proxy/data plane with routing, guardrails, OpenTelemetry tracing. Routing is done by a small purpose-built model (README: "4B-parameter" `plano_orchestrator_v1`; the earlier Arch-Router-1.5B maps queries to user-defined domain/action "preferences" without retraining, paper claims 93.17% routing accuracy, +7.71% over proprietary baselines — authors' own claim). The Arch-Router-1.5B weights are under the "Katanemo license" (not confirmed OSI-approved). No pricing/budget features described. — [GitHub](https://github.com/katanemo/plano); [Arch-Router paper](https://arxiv.org/html/2506.16655v1); [HF model](https://huggingface.co/katanemo/Arch-Router-1.5B.gguf); [Plano routing docs](https://docs.planoai.dev/guides/llm_router.html)
- **Cloudflare AI Gateway**: dynamic routing built as a flow (conditions, percentage splits, rate limits, budget limits, fallbacks); caching is exact-match only per 2026 comparisons. **Kong AI Gateway**: semantic routing (embed prompt vs per-target `semantic_description`), per-consumer-group dollar budgets using per-target `input_cost`/`output_cost`, returns 429 when exhausted; semantic features reportedly need Enterprise/Konnect and a vector store such as Redis. Sources are third-party/vendor-comparison pages (one published by a competitor gateway), plus Kong's own cookbook. — [Kong cookbook](https://developer.konghq.com/cookbooks/llm-cost-optimization/); [Cloudflare dynamic routing (preview mirror)](https://codex-container-api-docs.previews.developers.cloudflare.com/ai-gateway/features/dynamic-routing/index.md); [comparison](https://www.tooljunction.io/blog/ai-gateway-comparison-portkey-litellm-kong-cloudflare)
- **Smaller 2026 open-source newcomers**: `pareto-router` (MIT, 4 stars, v0.2.0; TF-IDF + ridge regression predicting per-model quality, λ cost knob and budget mode; claims matching top model quality at ~98% lower cost on a 12-model subset of LLMRouterBench, self-reported, tiny adoption); OpenZiti `llm-gateway` (zero-trust OpenAI-compatible proxy; 3-layer cascade: keyword heuristics -> embeddings -> LLM classifier); Aurelio Labs `semantic-router` (MIT, embedding-similarity route library, no LLM call). — [pareto-router](https://github.com/Keyan-sm/pareto-router); [openziti/llm-gateway](https://github.com/openziti/llm-gateway); [aurelio-labs/semantic-router](https://github.com/aurelio-labs/semantic-router)
- **Anthropic-native alternatives to routing**: (i) subagents with a per-subagent `model`; (ii) `opusplan` (strong model in plan mode, cheaper for execution); (iii) the **advisor tool** (experimental): a cheaper main model (e.g., Haiku 5.5/Sonnet 5.5) calls a stronger advisor model server-side at decision points; toggling it does NOT invalidate the main model's prompt cache, but each advisor call reads the full transcript uncached at advisor rates; not available on Bedrock/Vertex Agent Platform/Foundry. — [Claude Code advisor docs](https://code.claude.com/docs/en/advisor.md)

### Inferences
- For a self-hosted workspace the shortlist is: LiteLLM (budgets/virtual keys/tiers/session affinity, biggest ecosystem) as the control plane, optionally with vLLM Semantic Router (if you run local vLLM models and want Envoy-grade, policy-driven routing) or Plano (if you want a small routing model and agent orchestration). Hosted routers (Not Diamond, Martian, Requesty, OpenRouter Auto) add third-party data exposure and a per-token fee (Not Diamond $0.05/M tokens routed) with little independent proof of benefit.
- For task-typed workloads (chat vs summarization vs memory extraction vs file generation), the application already knows the task type; a rule table keyed on task, with a heuristic/LLM tier classifier only for the free-form "chat" bucket, avoids classifier cost and misrouting for most calls.
- The "advisor" and "small model drafts, big model reviews" patterns are an alternative to up-front routing that keeps one conversation on one model's cache.

### Gaps
- Could not verify current licenses of LiteLLM enterprise features, Kong AI semantic features, or Martian/Not Diamond self-host options from primary sources.
- No primary source on OpenRouter Auto's underlying engine (the docs page does not name Not Diamond or any vendor).
- Requesty/Martian/Not Diamond numbers are vendor or aggregator claims; no hands-on verification.
- Did not check Helicone/Bifrost/TensorZero/Envoy AI Gateway in depth (Bifrost appeared only in a competitor-published listicle).

## 2. Evidence: savings vs quality loss, and the known downsides

### Takeaway
Self-reported results show 40-85% cost reduction at ~87-97% relative quality, but independent benchmarking (LLMRouterBench, Jan 2026) found many routers perform alike and several, including commercial ones, fail to reliably beat a simple best-single-model baseline. Savings are real mainly when the model price gap is large (>10x) and the task mix has many easy requests; prompt-cache breaks and misrouting erode them.

### Cited Findings
- **FrugalGPT (2023)**: LLM cascade learns which models to try; abstract claims matching GPT-4 with up to 98% lower cost, or +4% accuracy at the same cost. These are experiments on the then-price spread (~2 orders of magnitude) and older models. — [arXiv 2305.05176](https://arxiv.org/abs/2305.05176)
- **RouteLLM (2024)**: ">2x" cost reduction with no quality loss in some cases (abstract); README claims up to 85% at 95% of GPT-4 on MT Bench and ">40% cheaper than commercial routers" (self-reported). — [arXiv 2406.18665](https://arxiv.org/abs/2406.18665); [GitHub](https://github.com/lm-sys/RouteLLM)
- **RouterBench (2024)**: 405k+ inference outcomes benchmark and a theoretical framework; abstract reports no specific savings numbers. — [arXiv 2403.12031](https://arxiv.org/abs/2403.12031)
- **LLMRouterBench (Jan 2026)**: 400K+ instances, 21 datasets, 33 models, 10 router baselines. Findings: models are complementary (routing is premise-valid), but many routers perform similarly, several recent/commercial routers "fail to reliably outperform a simple baseline", a large gap to the oracle remains due to model-recall failures, embedding backbone matters little, and careful model-pool curation beats bigger pools. A search summary says OpenRouter's router in particular did not reliably beat the best single model; I could not verify that from the abstract page itself (it does not name OpenRouter), so treat as unconfirmed. — [arXiv 2601.07206](https://arxiv.org/abs/2601.07206); [search summary](https://arxiv.org/abs/2601.07206v1)
- **May 2026 paper**: argues much reported "unsolvability" is evaluation artifact (13-17 pp routing opportunity cost), recommending dual-judge validation and exact-match anchoring; relevant to the reliability of LLM-judge-based router evaluations. — [arXiv 2605.07395](https://arxiv.org/html/2605.07395v1) (seen only via search snippet)
- **LiteLLM production case (vendor claim)**: 51.1% saving over a flagship-only counterfactual, rising from 42.9% to 60.7% as the tier map was tuned; the "88.1% matched or beat" is mostly ties (78.3% tie); caching study: routing 37-69% cheaper than caching a single fixed model. — [LiteLLM benchmarks](https://docs.litellm.ai/docs/auto_router/benchmarks)
- **TrueFoundry (vendor claim)**: 69% cost reduction on 550 prompts; LLM-classifier mode 66% cheaper at 95% quality relative to Opus. — [TrueFoundry blog](https://www.truefoundry.com/blog/engineering/llm-cost-routing-benchmark.md) (snippet only)
- **Prompt-cache break on model switch (primary)**: "Each model has its own cache. Switching ... means the next request reads the entire conversation history with no cache hits, even though the content is identical." Cache match is exact-prefix; effort level and fast mode also have separate caches on most models (effort change keeps the cache on Fable 5.1+, Opus 5.5, Sonnet 5.5, Haiku 5.5 with API key/subscription). Default TTL 5 minutes (1 hour available at higher write cost). A skill/command that names a different model is also a model switch. — [Claude Code prompt caching docs](https://code.claude.com/docs/en/prompt-caching.md)
- **Price structure that makes cache breaks costly (Anthropic pricing page)**: Sonnet 5.5 $2 in / $10 out per MTok, cache hit $0.10, 5m write $2.50, 1h write $4; Opus 5.5 $4 / $20, cache hit $0.20; Haiku 5.5 $0.10 / $0.50 (prompts <=100K; $0.50 / $2.50 above 100K), cache hit $0.01; Batch API gives 50% off input and output. A cache hit is 5% of base input price, so a mid-conversation switch to another model forfeits a ~20x discount on the accumulated context. — [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- **Other costs of routing**: semantic router adds ~100-500 ms and no session pinning in LiteLLM; classifier cost at most $0.61 per 1,000 requests in LiteLLM's tests; LiteLLM found that including assistant replies in classifier context lowered quality and raised cost, default is the last three user turns capped at 200 chars each. — [LiteLLM auto routing](https://docs.litellm.ai/docs/proxy/auto_routing); [benchmarks](https://docs.litellm.ai/docs/auto_router/benchmarks)

### Inferences
- With the 2026 Anthropic price ladder (Haiku 5.5 is ~20x cheaper than Sonnet 5.5 on input and output; Sonnet 5.5 is 2x cheaper than Opus 5.5), up-front routing between tiers is likely to save money mostly for short, stateless calls (classification, memory extraction, titles, summarization) and much less for long multi-turn chat, where cache economics dominate.
- Hard-to-measure quality loss is the main risk: vendor evaluations use LLM judges, single runs, and flagship-only counterfactuals. A shadow-evaluation harness on your own traffic (as LiteLLM suggests) is the credible validation method.
- Because decisions are cheap and pre-known for task-typed calls, a "route per task type, stick per conversation" policy sidesteps most documented failure modes of learned routers.

### Gaps
- No independent, peer-reviewed measurement of savings on agentic/long-context/document-generation workloads; all 2026 percentages for those come from vendors.
- Did not retrieve the full LLMRouterBench PDF to confirm router-by-router results (including OpenRouter).
- No data found on misrouting rate in production for task-typed assistants specifically.

## 3. Practical routing design for an assistant (rules vs classifier vs small-model-decides; stickiness; effort levels)

### Takeaway
Use a layered design: explicit task-type rules first, a cheap heuristic or small-LLM tier classifier only for ambiguous chat turns, per-conversation model stickiness with up-switching only at cache-cheap boundaries, and a user-facing effort setting mapped to (model tier, thinking budget).

### Cited Findings
- LiteLLM's design (heuristic scorer default; LLM classifier optional; keyword rules; custom plugin; tier-to-model/pool; session affinity pinning first-turn model; classifier fallback to heuristic; context-window escalation) is a ready-made reference for the "tiers + stickiness" pattern. — [LiteLLM auto routing](https://docs.litellm.ai/docs/proxy/auto_routing)
- LiteLLM reports its heuristic v2 cut cost per solved task ~45% and raised solve rate from 52.4% to 66.7% versus heuristic v1 on Terminal-Bench subset, and that "model-tier selection was as important as router selection" (via a benchmark summary) — i.e., which models populate each tier matters more than the classifier. — [LiteLLM benchmarks](https://docs.litellm.ai/docs/auto_router/benchmarks); [summary](https://intuitionlabs.ai/articles/ai-model-routing-cost-quality)
- OpenRouter's Auto Router exposes a `cost_tier` (low/medium/high) and picks "a model and reasoning effort" - an existing precedent for mapping a user-facing knob to model+effort. — [OpenRouter Auto Router](https://openrouter.ai/docs/guides/routing/routers/auto-router)
- Anthropic's own guidance: pick model and effort at session start and save `/compact` for natural task breaks; `opusplan` (Opus for planning, Sonnet for execution) causes a cache restart each time plan mode toggles; subagents get their own system prompt/cache and do not disturb the parent's cache; forks that inherit the parent prefix can read the parent's cache. — [Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching.md)
- Delegation instead of switching: a subagent call or an advisor call lets a different model do a bounded sub-task while the main conversation stays on one model/cache. Subagent TTL defaults to 5 minutes. — [prompt caching docs](https://code.claude.com/docs/en/prompt-caching.md); [advisor docs](https://code.claude.com/docs/en/advisor.md)
- Small routing models exist if "small model decides" is wanted: Arch-Router-1.5B / Plano-Orchestrator (4B) map prompts to user-defined policies. License caveat: Katanemo license. — [Plano](https://github.com/katanemo/plano); [Arch-Router](https://arxiv.org/html/2506.16655v1)
- Batch API (50% discount) suits non-interactive tasks (memory extraction over history, bulk summarization, deep-research page reading offline). — [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)

### Inferences (proposed design; not sourced as a single recommendation)
- Layer 0 rules by task type: memory extraction, titles/tags, language detection, summarization of a single document, reranking -> small/cheap tier (Haiku 5.5-class, or open model like Qwen/DeepSeek-Flash-class) with structured output; deep research: planner/synthesizer on a strong tier, page readers/extractors on a cheap tier (fan-out parallel, cheap-tier input is the bulk of tokens); vision/page reading -> VLM tier; file generation -> code-capable mid tier with a sandbox and verify/repair loop (see sections 5-6); hard reasoning -> strong tier with high effort.
- Layer 1 (chat only): heuristic scorer or tiny LLM classifier on the last ~3 user turns; decide once on the first turn and pin the conversation (session affinity). Allow only deliberate escalation (user clicks "think harder", repeated failure, tool error loops, context overflow), accepting one cache rebuild, ideally when the TTL has already expired.
- Effort mapping example: Low = cheap tier, no extended thinking; Medium = mid tier, small thinking budget; High = strong tier, large thinking budget. Because effort changes also invalidate caches on some models, fix effort per conversation or per message-turn boundaries; Claude 5.5-generation models are documented to keep cache across effort changes.
- Per-user/per-key budgets belong in the gateway (LiteLLM virtual keys, Kong consumer groups, Cloudflare/Requesty budgets), with a degrade-to-cheaper-tier policy at budget thresholds rather than a hard 429.

### Gaps
- No peer-reviewed evidence comparing rules vs classifier vs LLM-decides for assistant products specifically.
- Exact behavior of Thompson-sampling "adaptive" pools on cache hit rate not documented.
- Non-Anthropic providers' cache semantics (OpenAI automatic prefix cache, Gemini implicit/explicit cache, DeepSeek disk cache) were not researched here; they are also model-scoped in practice but I have no source in these notes.

## 4. Specialized small/distilled models (OCR/parsing, extraction, embeddings/rerank, GUI/computer use, cheap generalists)

### Takeaway
Task-specific small models are strongest in document parsing/OCR (sub-1.5B VLMs now beat much larger general VLMs on OmniDocBench), embeddings/reranking (Qwen3 0.6B-8B, Apache-2.0), and structured extraction (NuExtract 2B-8B, MIT). For GUI/computer use, open models trail frontier closed models but are improving; for "build a PDF/XLSX/PPTX" there is no dedicated distilled model found: the reliable approach is a general code-capable model plus templates/skills and a verify loop.

### Cited Findings
- **Document parsing / OCR**
  - MinerU: ~83.9k stars; custom "MinerU Open Source License" (Apache 2.0 plus additional conditions); converts PDFs/scans/Office/EPUB/HTML to Markdown/JSON; four parsing tiers (flash/basic/standard/advanced) with download sizes from ~0.8 GB to ~3 GB; v4.2 latest named. — [GitHub](https://github.com/opendatalab/MinerU)
  - Docling (IBM/LF AI): MIT code, ~70.8k stars; runs locally/air-gapped, `docling-serve` API, supports Granite-Docling VLM (name suggests 258M params; page does not state it). Model licenses are separate. — [GitHub](https://github.com/docling-project/docling)
  - DeepSeek-OCR: MIT, ~24.2k stars; visual-text compression: 64/100/256/400 vision tokens at 512/640/1024/1280 px modes; ~2500 tokens/s on an A100-40G with the vLLM PDF script; successor DeepSeek-OCR2 released Jan 2026 (separate repo). — [GitHub](https://github.com/deepseek-ai/DeepSeek-OCR)
  - PaddleOCR-VL-0.9B: Apache-2.0; paper reports OmniDocBench v1.5 overall 92.86 vs MinerU2.5-1.2B 90.67, and ~15.8% higher page throughput; later 1.5 version reported 94.5; different versions' numbers differ (96.33 belongs to a newer 1.6 per one reviewer). Authors' own benchmark results. — [alphaXiv/paper](https://arxiv.org/pdf/2510.14528v4); [secondary review](https://lilting.ch/en/articles/paddleocr-vl-1-5-document-parsing)
- **Structured extraction**: NuExtract (NuMind) fine-tuned from small bases (original Phi-3) on synthetic data labeled by a larger LLM (Llama 3 70B) — an explicit distillation recipe. NuExtract 2.0 open versions 2B-8B (vision-capable), MIT license; vendor claims they beat GPT-4o/GPT-4.1 on extraction; vendor says fine-tuning still needed for domain data. No independent replication found. — [NuMind blog](https://numind.ai/blog/nuextract-2-0-takes-the-lead-in-information-extraction) (also at [numind.ai/blog/outclassing-frontier-llms----nuextract-2-0-takes-the-lead-in-information-extraction](https://numind.ai/blog/outclassing-frontier-llms----nuextract-2-0-takes-the-lead-in-information-extraction)); [NuExtract original](https://numind.ai/blog/nuextract-a-foundation-model-for-structured-extraction)
- **Embeddings and reranking**: Qwen3-Embedding and Qwen3-Reranker, each in 0.6B/4B/8B, Apache-2.0; the 8B embedding model scored 70.58 on MTEB Multilingual (June 2025; ranking may since have changed); rerankers are not evaluated on MTEB. — [arXiv 2506.05176](https://arxiv.org/html/2506.05176v3)
- **GUI/computer use**
  - UI-TARS-1.5 (ByteDance): Apache-2.0, ~11.7k stars; open weights for UI-TARS-1.5-7B (full 1.5 model via research access only); OSWorld 42.5 (100 steps) for full model, 27.5 for 7B, 24.6 for 72B-DPO. — [GitHub](https://github.com/bytedance/UI-TARS)
  - UI-TARS-2 report: 47.5% OSWorld in the paper; a leaderboard entry lists UI-TARS-2-2509 at 53.1% on OSWorld-Verified (100 steps); settings not comparable. Qwen3-VL-235B scores vary 38.1% to 66.7% depending on scaffold across aggregator pages (unreliable). I found no verified data on GLM-4.6V computer use; AutoGLM-OS-9B (built on GLM-4.1V-9B-Thinking) reported 48.9% OSWorld in the ComputerRL paper. A July 2026 leaderboard snapshot lists MiniMax-M3 as top open-weight at 75.2% (aggregator). — [UI-TARS-2 paper](https://arxiv.org/abs/2509.02544); [leaderboard aggregator](https://yutori.com/leaderboards/osworld-verified.md); [OSWorld ranking](https://www.developersdigest.tech/models/best-for/computer-use)
- **Cheap generalist open-weight models for code/structured output (mid-2026 snapshot, aggregator blogs)**: DeepSeek V4-Flash list price $0.14 in / $0.28 out per M tokens; V4-Pro ~$0.435 / $0.87 (one source says $2.48 output; conflict); GLM-5.2 is the top open-weight model on Artificial Analysis Intelligence Index v4.1 (51) vs DeepSeek V4-Pro 44 and Kimi K2.6 43; SWE-bench Pro: GLM-5.2 62.1%, Kimi K2.6 58.6%, DeepSeek V4-Pro 55.4%; SWE-bench Verified: V4-Pro 80.6%; V4-Pro produced ~4x median output tokens, shrinking per-task savings. Qwen3.7-Max reported 60.6 on SWE-bench Pro. — [codersera comparison](https://codersera.com/blog/kimi-k2-6-vs-deepseek-v4-vs-glm-5-1-2026/); [OpenRouter open-weight models June 2026](https://openrouter.ai/blog/insights/the-open-weight-models-that-matter-june-2026/); [kimchi.dev GLM-5.2](https://kimchi.dev/blog/glm-5-2-vs-frontier-what-the-data-says); [contextstudios](https://www.contextstudios.ai/blog/deepseek-v4-the-open-source-pricing-earthquake)
- **Cheap proprietary tier**: Claude Haiku 5.5 at $0.10 in / $0.50 out per MTok (prompts <=100K), cache read $0.01. — [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)

### Inferences
- Parsing pipeline recommendation: parse files once with MinerU/Docling/PaddleOCR-VL/DeepSeek-OCR, cache Markdown + page images, and feed the LLM text (cheap) rather than raw PDFs/images each turn; send page images to a VLM only for charts/figures or low-confidence pages.
- Embedding + reranker (Qwen3 0.6B or 4B, Apache-2.0) are the clearest "small model, big saving" components for RAG/memory retrieval; run on a single GPU/CPU.
- Memory extraction and summarization are good fits for the cheapest tier (Haiku-class or an open Flash-class model) with JSON-schema-constrained output; NuExtract-class models are an option if you need fully local extraction.
- Prices for open-weight models vary by host; treat the June-2026 blog numbers as indicative and re-check OpenRouter/provider pages.

### Gaps
- No dedicated small/distilled model found specifically for generating PDF/XLSX/PPTX/DOCX (searched; none surfaced).
- Did not retrieve Hugging Face model cards directly (licenses for Qwen3-VL, GLM-V, GUI-Owl, MinerU2.5 weights, Granite-Docling not individually confirmed). MinerU2.5's parameter count (1.2B) comes only from the PaddleOCR-VL comparison text.
- No November 2026 leaderboard data for open vs closed model coding quality; sources are May-July 2026 blogs.
- Summarization-specific distilled models (e.g., small summarizers) not researched.

## 5. File/artifact generation approaches (PDF, XLSX, DOCX, PPTX), open-source projects, which work with cheaper models

### Takeaway
Claude and ChatGPT-style products generate office files by having the model write code (python-docx/openpyxl/python-pptx or docx-js/pptxgenjs) in a sandbox, then converting/rendering with LibreOffice for verification. Anthropic open-sourced these "document skills" (Apache-2.0), which are the best reusable blueprint. Markup-first routes (Markdown -> Marp/Pandoc, HTML -> Playwright PDF, Typst) are easier for weaker models; direct python-pptx is the least forgiving.

### Cited Findings
- **How Claude does it**: files are created in a sandbox with code execution ("Code execution and file creation" toggle); xlsx, pptx, docx, pdf; 30 MB per file limit; network access is off by default on Team orgs. Third-party reviewer: "it's a code interpreter" (Claude writes Python/Node, runs, returns files). — [Anthropic support article](https://support.claude.com/en/articles/12111783-create-and-edit-files-with-claude); [eesel review](https://www.eesel.ai/blog/claude-docs-review)
- **Agent Skills API**: pre-built skills `pptx`, `xlsx`, `docx`, `pdf` run via the code execution tool in the `container` parameter; generated files downloadable only through the Files API; Skills not covered by ZDR. Code execution is billed by container time unless used with web search/fetch. — [Skills quickstart](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/quickstart); [Skills guide](https://platform.claude.com/docs/en/build-with-claude/skills-guide); [pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- **anthropics/skills repo**: ~197k stars; document skills (docx, pdf, pptx, xlsx) stated as Apache-2.0 in the README (README also says "for demonstration and education", test before relying; check THIRD_PARTY_NOTICES). — [GitHub](https://github.com/anthropics/skills)
- **pptx skill internals**: create new decks with **pptxgenjs** (Node); python-pptx listed as limited alternative; edit/template path = unpack .pptx and edit `ppt/slides/slideN.xml`, repack, validate; verification = text extraction, `validate.py`, then render with **LibreOffice** (`soffice`) to PDF, **pdftoppm** to JPEG, and visually inspect for overflow/overlap. — [pptx SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/pptx/SKILL.md)
- **xlsx skill internals**: openpyxl + pandas; openpyxl writes formulas with no cached values so a LibreOffice recalculation script runs and reports errors; write formulas not Python-computed values; avoid XLOOKUP/FILTER/UNIQUE etc. (use INDEX/MATCH, 2007-era functions; `_xlfn.` prefix for six newer ones); never save a workbook loaded with `data_only=True`. — [xlsx SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/xlsx/SKILL.md)
- **Slide format reliability**: practitioner write-ups recommend Marp (near-CommonMark Markdown, headless render, native pptx export) as most LLM-friendly; python-pptx gives editable output but hand-built layout and unpredictable template layout inheritance (use blank layouts); HTML -> Playwright -> PDF/PPTX (html2pptx-style conversion) is a newer approach; Typst gives excellent PDF but no PowerPoint. No head-to-head reliability data for cheap models found. — [Zenken on Marp](https://ai.zenken.co.jp/en/post/chatgpt-slide-making/); [nbrosse comparison](https://nbrosse.github.io/posts/llm-slides/llm-slides.html); [slide-generation tech log](https://ice-ice-bear.github.io/posts/2026-05-29-the-ai-slide-generation-rabbit-hole/); [arXiv 2601.09487](https://arxiv.org/pdf/2601.09487.pdf) (slide benchmark across PPTX and HTML; snippet only)
- **Benchmarks of office-file work (2026)**: OfficeEval/"Mind the Gap" (arXiv 2606.10956, 200 tasks, 7,118 checkable criteria, 7 frontier models): single-turn models weak, code-execution failures caused most zero scores especially on PPT/Excel, coding agents improved PowerPoint scores substantially (python-pptx lacks some constants COM exposes). OmegaUse-OfficeVal (arXiv 2607.27155, 100 long-horizon tasks across DOCX/PPTX/XLSX/PDF): Word and Excel better than PowerPoint and mixed-file tasks; Qwen3.7-Plus top on time-weighted score, GLM-5.2 top on average quality (per search summary; open-weight status not confirmed in the snippet). — [OfficeEval](https://arxiv.org/html/2606.10956); [OmegaUse-OfficeVal](https://arxiv.org/pdf/2607.27155)
- **Open-source projects**:
  - Presenton (Apache-2.0; open-source AI presentation generator; PPTX/PDF export; works with OpenAI, Gemini, Anthropic, Ollama, LM Studio; star counts inconsistent, one directory snapshot ~2.1k, verify live) — [GitHub](https://github.com/presenton/presenton); [docs](https://docs.presenton.ai/general/overview)
  - excel-mcp-server (haris-musa; MIT; ~4k stars; workbooks, charts, pivots, formatting via `uvx excel-mcp-server`) — [GitHub](https://github.com/haris-musa/excel-mcp-server)
  - Other Word/PowerPoint MCP servers (e.g., dosev-ai mcp-office suite, ~4 stars) are small and unproven; I did not find a well-starred Word MCP server. — [directory](https://skillselion.com/mcp/tool/io.github.dosev-ai/mcp-office-word)
  - Claude Code document skills (anthropics/skills) are installable as a plugin (`document-skills@anthropic-agent-skills`). — [GitHub](https://github.com/anthropics/skills)

### Inferences
- Architecture recommendation for a self-hosted workspace: copy the Anthropic skill pattern (SKILL.md instructions + helper scripts for unpack/validate/render + LibreOffice render-and-inspect loop) and make the model's job small: emit a structured spec (JSON/Markdown of slides, sheets, sections) and let deterministic code (your own templates built on pptxgenjs/python-pptx/openpyxl/docx-js) render it. This is the main route to make cheap models reliable; the failures documented in OfficeEval are mostly code-execution errors, which a templated renderer removes.
- Tiering: spec/outline/content writing on a mid tier; deterministic render; a cheap VLM or heuristics for visual QA of rendered pages; escalate to a stronger model only after repeated validator failures.
- PDF: for reports use Markdown/HTML -> PDF (Playwright/WeasyPrint) or Typst; for forms/editing existing PDFs use libraries as in Anthropic's pdf skill. DOCX: docx-js or python-docx with a house template; PPTX: pptxgenjs/python-pptx with branded template layouts or Marp.
- LibreOffice is the key shared dependency (recalculate XLSX formulas, render PPTX/DOCX to PDF for QA), so the sandbox image should include it, fonts, poppler.

### Gaps
- No controlled study of cheap-vs-frontier models on python-pptx/openpyxl/docx-js generation reliability; only inference from OfficeEval/OmegaUse summaries.
- I did not retrieve ChatGPT's file-generation internals (not documented in sources I fetched), nor docx and pdf SKILL.md contents (docx skill reportedly uses docx-js; not verified here).
- Stars/licenses for Marp, pptxgenjs, python-pptx, python-docx, openpyxl, Typst, Pandoc were not fetched; Anthropic's skill confirms use of pptxgenjs, openpyxl, LibreOffice, poppler.
- OmegaUse-OfficeVal per-model open-vs-closed numbers not retrieved.

## 6. Sandboxing code execution (E2B, Daytona, Docker, gVisor, Pyodide) and costs

### Takeaway
For self-hosting, a locked-down container/gVisor or Firecracker-based runner is needed; managed sandboxes (E2B) bill roughly $0.05/vCPU-hour + $0.016/GiB-hour per second. Daytona's open-source repo was archived in Oct 2026, so it is no longer a safe open-source dependency.

### Cited Findings
- **E2B**: Apache-2.0, ~14.9k stars; code-interpreter SDK (Python/JS); self-hosting via separate infra repo (`e2b-dev/runtime`) deployed with Terraform on AWS/GCP/Azure/Linux. Isolation tech is not stated on the repo page; third-party comparisons say Firecracker microVMs. — [GitHub](https://github.com/e2b-dev/E2B); [comparison](https://www.morphllm.com/comparisons/e2b-vs-daytona)
- **Pricing (third-party, May-Oct 2026 blogs)**: E2B and Daytona both about $0.0504 per vCPU-hour and $0.0162 per GiB-hour, billed per second; E2B Pro plan $150/month; a 2 vCPU/4 GiB sandbox about $0.1656/hour; Daytona usage-based with $200 free credit; Modal Sandboxes (gVisor) ~41% pricier per vCPU. Verify on vendor pages. — [Fly.io sandbox pricing](https://fly.io/learn/ai-sandbox-pricing/); [Activepieces E2B guide](https://www.activepieces.com/blog/e2b-pricing-plans-rates-and-limits-2026-guide); [agent37](https://www.agent37.com/blog/e2b-pricing); [startuphub comparison](https://www.startuphub.ai/news/daytona-vs-e2b-vs-modal-vs-vercel-sandbox-2026)
- **Daytona**: ~71.3k stars; its GitHub repo is **archived and read-only (archived 2026-10-03)**; core development moved to a private codebase; "no further updates, fixes, or releases". Sandbox described as dedicated kernel, filesystem, network stack. — [GitHub](https://github.com/daytonaio/daytona)
- **Anthropic's hosted code execution** is billed by execution time (free when used with web search/fetch tools) and Managed Agents replace container-hour billing with session runtime. — [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)

### Inferences
- Document generation is short-lived CPU work (seconds, a few hundred MB), so even per-second managed sandboxes cost fractions of a cent per file; the dominant cost is LLM tokens, not compute. Self-hosting is justified mainly by data-control/egress needs.
- Reasonable self-hosted options (not researched in sources here): Docker with seccomp/read-only rootfs/no network, gVisor runtime for stronger isolation, Firecracker via E2B's self-host runtime; Pyodide (WASM) can run python-docx/openpyxl in-browser but cannot run LibreOffice, so rendering/recalculation would still need a server-side container.

### Gaps
- No sourced comparison of gVisor vs Firecracker vs Docker isolation, no Pyodide capability source, no cold-start benchmarks beyond aggregator mentions (a "sandbox benchmark 2026" post exists at hub.superagent.sh but was not read).
- Daytona and Modal pricing details are aggregator-sourced.
